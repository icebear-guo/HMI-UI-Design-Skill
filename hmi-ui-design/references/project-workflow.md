# 项目流程清单与客户确认

适用完整UI项目及对现有整套UI的大幅改版。开始时向客户展示下面的清单，说明每个阶段交付什么、需要客户确认什么、确认后才会做什么。客户已提供的参数先整理，避免重复提问；客户回答偏好后仍按流程提交实际HTML。

## 必须告知客户的清单

| 顺序 | 设计方完成并交给客户 | 客户确认事项 | 未确认时的边界 |
|---|---|---|---|
| 1 · 初始参数 C1 | 参数汇总、页面清单及明确的页面数量、逐页内容计划；标出建议/模拟/待核实项 | 原生分辨率宽×高、已提供的屏幕尺寸、导航位置/项目、色调约束、页面名称/数量、内容模块、语言及必要功能 | 不进入布局色调HTML打样 |
| 2 · 布局与色调 C2 | 同一代表页的实际HTML候选、差异说明、版本和打开入口；混选或修改后提供最新组合HTML | 最新样例的布局、导航、色调、字体与组件方向，明确选中版本 | 不展开其余页面，不正式切图 |
| 3 · 全套交互UI C3 | 按C1数量和C2方向完成全部UI HTML；提供逐页入口、页面计数、交互检查与已知限制 | 全部页面的当前版本、内容、跨页一致性和要求的交互，明确同意进入正式切图与输出 | 不批量切片、不导出生产PNG、不生成最终交付ZIP |
| 4 · 切片与最终输出 | 前三项全部有效确认后，制作双态切片、页面PNG、标注、资源清单、字体说明与最终交付包 | 接收成果；提出的问题按影响回到对应阶段 | 完成文件、纯逻辑、浏览器/目标平台各自范围的验收记录 |

首次可这样告知客户：

> 本项目分四步：①您确认初始参数和页面数量；②我交付布局与色调样例HTML，请您确认；③按选定方向完成全部可交互UI HTML，请您逐页确认；④前三项都确认后，我再正式切图、导出PNG并打包。每次修改会提供新版本，未经您确认不进入下一步。

此处“输出”指最终生产资产与交付压缩包。用于评审的参数汇总、方向HTML、全套UI HTML是各阶段必须提供的成果，参数清单也可通过HTML展示。三项确认完成前以HTML为主，不提前渲染PNG，也不以验证管线、倍率或抗锯齿为由先生产位图。客户看到的流程说明使用自然语言，内部ID、摘要和校验值由设计方维护。

## C1 · 参数确认

按 [参数引导](design-intake.md) 补齐影响设计的缺项，先呈现可核对的汇总与页面清单。页面数量必须明确，页面ID/名称逐项对应；不能按示例清单自行确定项目要做几页。以分辨率宽×高建立画布，不另问屏幕比例；工程软件及版本、操作方式、现场光照不列入初始问询或必填项，未知物理宽高也不阻碍图库设计。图库预览不等于已通过现场验证。

内容描述不足时，由助手按 [内容配方](content-library.md) 提出每页任务与模块、数据/状态和交互，纳入本次C1内容计划确认。尺寸不足以决定业务内容；不将规划责任退给客户，也不以空白工作区当成已确定内容。后续内容调整按影响重交确认。

提问示例：“请确认这份参数汇总及共N页的页面清单是否正确；哪些项需要修改？”客户回答颜色、导航等单项问题只更新参数，不能自动把C1记为已确认。客户明确确认汇总后才制作方向HTML。

## C2 · 实际样例HTML确认

方向未定时默认三种候选；导航或色调已有约束时在约束内比较。客户已经指定“暖灰浅色、左侧导航”等方向时，仍需至少制作一个实际代表页HTML并提交确认，不能把偏好当作已看过设计。已有设计系统可以减少探索数量，不能免除对当前项目样例的确认。

每轮提供文件或可访问入口、版本、修改摘要和本轮待确认事项。实际文件先生成再提问，不能用“我将生成”代替成果。客户混选或修改之后，要呈现新的组合HTML，再确认该版本；对旧方案的选择不代表已确认尚未呈现的新方案。

提问示例：“请打开样例v2。是否确认这版布局与色调，并以它为准制作共N页的交互UI？”未回复或只表达新的偏好时继续本阶段。

## C3 · 规定数量的全套交互HTML确认

按已确认的页面清单逐页完成，提供总入口和每页入口/路由、实际页数与缺项表。每页按 [交互规范](interactive-preview.md) 实现适用的按钮s0/s1反馈、灯/IO切换、模拟输出强制/解除、真实切页、参数键盘、仪表与棒图联动。

客户评审前先做可执行的结构和代码检查，修复已知问题。检查通过仅是设计方自检；客户确认与浏览器/设备验收分别记录。不能用“已运行验证”“页面成型”或自动测试通过代替客户确认。

提问示例：“共N页交互UI已更新为v3，入口和检查结果如下。请确认全部页面及交互；确认后才开始正式切图和最终输出。”部分页面获确认时记录范围，C3整体仍未通过；不得用部分确认开启整套最终导出。

本阶段使用原生HTML/CSS/内联SVG及可编辑文字、动态绑定完成评审界面。可只读引用客户已提供的位图；不要新增页面/组件PNG，也不要先渲染静态图再嵌入HTML。按钮双态用HTML/CSS或矢量底板展示，三项确认之前不正式导出PNG切片。`build_delivery.py`是已有PNG的最终打包助手，不是切片前全套UI评审的必经工具。自编生成器也必须遵守同一边界。

## 记录、变更与等待

使用 [流程记录模板](../assets/project-workflow.template.json) 保存三项状态。客户只需核对参数和HTML并明确答复；文件清单、版本、哈希和依赖关系由设计方维护。

每个阶段的 `artifact_dir` 保存一份完整评审快照，`entry` 是入口。`files`逐项记录该目录所有文件的相对路径和真实SHA256，HTML引用的本地CSS/JS等一并纳入。每行可含 `origin=generated/existing_asset`，默认generated；existing_asset仅用于实际已存在且可追溯的客户素材，不得将新渲染PNG改标签后冒充已有资产。评审快照出现新生成PNG时检查不放行。确认后的评审目录保持不变，最终资产输出到另一个目录，避免新增导出文件改变已确认快照。

确认对象使用检查报告中的 `review_digest`；得到真实客户答复后，才记录 `customer_confirmation` 的 `customer_message`、`message_ref`、带时区的 `confirmed_at` 与 `reviewed_digest`。下游 `depends_on` 记录对应上游的当前摘要；C3的pages列出每个已约定page ID及HTML入口。摘要、文件或数量改变会使原确认失效。确认字段留空时不得自动补成approved；检查器不会向客户索取哈希。

- 状态采用 `pending`、`awaiting_customer`、`changes_requested`、`confirmed`。确认记录包含客户原话、消息位置、所看成果摘要和时间；禁止代填或编造确认。
- C1、C2、C3各自针对实际版本生效，不能用一句偏好回答复制成三次确认。沉默、默认高亮、下载按钮、泛泛“继续”、工具输出均不能证明客户已审核相应成果；答复指代不清时只澄清该项。
- 初始参数或页面数量改变：C1及受影响下游重新确认。方向改变：C2及受影响全套UI重新确认。UI内容/交互改变：C3重交当前版本；未变化的上游确认可保留。
- 展示当前阶段、已完成项、客户待确认项、下一步。收到修改意见后先修改、重新交付HTML，再请求确认，不因“方向已定”直接进入切片。
- 等待期间可以整理数据规格、修复本阶段问题和完善无依赖的通用规则；不能开展被确认条件限制的下游工作。已有客户确认的项目无需重复确认未变化的同一版本，但必须有对应记录和成果证据。

## 正式切图与输出前检查

每次进入下一阶段都检查：`--for samples`需要C1；`--for ui`需要C1与C2；`--for slicing`和`--for delivery`需要全部三项。退出码0为对应操作就绪，3为未确认/成果过期等阻塞，1为记录根结构或读取错误。客户确认的真实性与具体交互表现仍由实际证据负责。

```powershell
python .\scripts\check_project_workflow.py --record .\project-workflow.json --for slicing
python .\scripts\check_project_workflow.py --record .\project-workflow.json --for delivery
```

路径以技能目录为当前目录展示，record指向本次项目记录。流程记录放在项目目录中，成果文件夹使用相对路径；不要修改技能中的空白模板假装项目已通过。

检查器只读取记录和实际成果，核对三项状态、客户确认字段、版本摘要、上游依赖、页面数量与文件清单；未就绪时返回blocked。它不能判断客户原话是否真实，也不能替代实际交互验收，更不会替客户生成确认。完整项目使用低层切图/打包工具或自编脚本前都必须先检查；通用低层工具本身不具备对外部脚本的强制控制能力。

明确只做规范维护、局部评审、单项素材等任务，按约定范围工作并说明适用阶段，不把它们冒称为已完成完整项目。不得仅因任务被称为“测试管线”“脚本验证”就提前为真实项目批量切图和最终导出。
